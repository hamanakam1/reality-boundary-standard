# Codex task — Review, refine, and prepare the Reality Boundary Standard for publication

## Invocation

Execute this prompt only when the publisher asks you to work on the standard. Preparing or editing the prompt is not a release instruction. This is independent of any client engagement; do not require private customer evidence to make the generic standard useful.

Read README.md, standard/STANDARD.md, standard/CONFORMANCE.md, GOVERNANCE.md, LICENSING.md, docs/PUBLICATION.md, schemas, examples, validator documentation, and the current change history. Read applicable repository instructions and preserve unrelated work.

## Outcome

Produce a coherent, exhaustive initial standard with a clear boundary among observed results, executed demonstrations, engineering proposals, research, speculation, and unknowns. Preserve separate support and deployment axes. Deliver a public-safe release candidate, concrete review findings, meaningful validation, and a publication packet. Publish only within the destination/content/visibility/license authority actually supplied by the owner.

## Normative review

Review each stable requirement for purpose, applicability, exact obligation, feasible evidence, proportionality, and conflicts with other requirements. Distinguish MUST from SHOULD and informative explanation. Avoid creating new paperwork where one concise field or existing record suffices. Do not treat every research uncertainty as a production blocker unless the production decision depends on it.

Check the standard's treatment of source provenance and dependency changes; sample/denominator/time/units; supporting and contradictory evidence; independent replication; historical truth; inference and causality; model evaluation and data rights; runtime authority and revocation; recovery and uncertain outcomes; tenancy and privacy; cryptographic verification boundaries; physical models and constraints; costs and commercial rights; portability; publishing; and accountable ownership.

Test the classification using difficult examples: a failed experiment; a deployed service with an unverified performance claim; a supported proposal rationale but unbuilt capability; a historical result whose scope remains valid; private evidence with a disclosed reviewer; a vendor announcement versus account access; a speculative system containing real subcomponents; and an apparently contradictory source covering a different version.

## Evidence and source review

Use primary sources when making factual technical claims. Fetch the actual relevant source, record its version/date, and keep the summary proportionate. Do not imply that referenced institutions endorse this project. A popular article, model agreement, or repeated claim is not independent evidence.

Avoid broad scientific verdicts where the actual issue is missing implementation evidence. Unverified does not mean impossible. Where a claim conflicts with an established constraint, cite the source supporting that exact conclusion. Keep fictional narrative separately labeled instead of laundering it into the standard's capability examples.

## Schemas and validator

Review whether the schemas and validator cover their stated field and policy contracts. Verify duplicate IDs, evidence references, date handling, unknown fields, missing results, contradictory evidence, operational use restrictions, authority applicability, and error behavior. Exercise valid scoped observations and invalid capability promotions. Check that all fixtures are clearly synthetic and that a synthetic fixture cannot be mistaken for operating evidence.

Do not claim the reference validator implements all of JSON Schema, authenticates sources, checks scientific truth, confirms legal authority, or determines full conformance unless those capabilities actually exist and are demonstrated. Keep structural validation, declared-policy checks, evidence review, and conformance outcomes separate in output and exit behavior.

## Review and iteration

Have a separate review pass examine the exact candidate for contradictions and false assurance. Give it explicit scope and counterexample tasks; do not treat another agent's agreement as empirical validation. Resolve material issues and preserve the reasoning. Keep optional polish bounded once the candidate meets its stated review goal.

Update stable requirement IDs only when needed; preserve or deprecate historical meanings with migration notes. Update the change log, source references, schema/version notes, and release manifest together. Do not set version 1.0 merely because the draft is long.

## Publication boundary

Select only this public source tree. Do not include private prompt packs, client Docs, browser sessions, customer records, source repositories, brainstorm transcripts, or hidden files with credentials. Inspect the exact Git history and remote metadata before pushing. Public examples should be independently written and generic.

Resolve the intended GitHub owner/organization, repository name, visibility, maintainers, and license from the owner's actual instructions. If absent, finish the complete candidate and ask for only those publication inputs as the final step. Explain the concrete missing decision. Do not create a public remote under a guessed account or assign a license to third-party work.

If the exact publication has already been authorized, use current authenticated tooling to publish, then read back metadata, commit, file content, and release status. Report the actual URL. If publication is blocked by access or automatic approval review, state the exact action and reason and preserve the ready candidate.

## Required outputs

- Revised standard/procedure/templates/schemas/examples where justified.
- Review report with exact requirement/file references and dispositions.
- Actual local verification results and explicit limitations.
- Public-content/reuse-rights review result.
- Release manifest and change notes.
- Completed publication metadata if published, otherwise the exact remaining input and ready-to-publish candidate.

Finish with the outcome, substantive changes, verification, remaining limitations, and next release decision. Avoid certification language, invented adoption claims, and statements that a publication operation succeeded before readback confirms it.
